# Navo 项目说明

## 一句话

Navo 是面向工业 B2B 团队的账户研究与外联协作工作台：它把分散的账户信息和外部证据，整理成可解释的资格判断、可复核的外联内容，以及有明确负责人的下一步行动。

## 我想解决的问题

工业 B2B 销售不是“生成一封邮件”这么简单。

真正困难的是一连串相互依赖的判断：

- 哪些账户值得投入时间；
- 判断依据来自哪里；
- 哪些内容是事实，哪些只是推断；
- 什么情况下应该继续研究、准备外联或停止；
- 模型生成的内容怎样进入真实工作流；
- 收到回复后，下一步由谁负责；
- 系统出错、重试或重复接收事件时，如何避免产生冲突结果。

因此我没有从聊天框或功能列表出发，而是先定义了一条完整的操作链：

```text
Accounts → Signals / Evidence → Research → Qualification → Contacts
→ Mission / Play → Message / Sequence → Replies → Next Best Action
```

页面、数据结构、执行边界和测试都围绕这条链展开。

## 我的角色

我主导了这个项目的产品定义与系统规划，包括：

- 产品定位和核心用户任务；
- 信息架构、页面优先级和跨页面操作链；
- Mission 的执行步骤、状态变化与停止条件；
- 模型、确定性代码和人工审核之间的职责划分；
- 证据、信号、推断、资格判断和人工决定的数据语义；
- 账户数、迭代次数、续接次数、外部动作和重复事件的边界；
- 演示数据、验收标准、回归测试和真实模型 smoke test；
- 竞品模式选择、界面密度、响应式顺序和作品展示方式。

编码助手承担了局部实现、检查和复审工作，但产品方向、任务拆分、取舍标准和最终验收由我控制。遇到建议与真实仓库、接口或测试结果冲突时，以可运行的系统事实为准。

## 五个关键判断

### 1. 先完成一条闭环，而不是扩展更多页面

我把 Account、Mission、Approval、Inbox 和 Analytics 作为首要工作区。Agents、Tools、provider、token、cost 和基础设施页面被主动降级，因为它们不能帮助销售操作员完成当前任务。

这让作品能够在几分钟内讲清楚，而不是依赖大量页面制造“功能很多”的印象。

### 2. 事实、推断和决定必须分开

外部网页内容先保存为可追溯证据，资格判断引用这些证据，系统建议不覆盖持久化事实，最终外联动作由人工决定。

这样做的目的不是增加标签，而是让每一个商业判断都能回答三个问题：

1. 信息从哪里来；
2. 谁做出了判断；
3. 哪个结果真正进入了工作流。

### 3. 模型只负责适合它的判断

模型用于结构化规划、研究摘要、信号提取和文案准备。线性调度、身份、状态转换、幂等、次数限制和后置校验由代码负责。

我没有让模型决定所有下一步，因为很多流程节点本身是确定性的。减少不必要的模型调用，也减少不可解释的状态变化。

### 4. 人工审批是业务流程，不是安全口号

外联内容可以编辑、要求修改、批准或拒绝。待审批状态允许操作；决定落库后变成只读记录。系统不会因为“已经生成”就把内容视为可以发送。

审批页因此被设计成消息、证据和决定并列的工作台，而不是一个单独的确认按钮。

### 5. 展示的数据必须能够追溯

Analytics 最初存在硬编码环比、模拟趋势和无实际行为的筛选器。为了作品可信度，我删除了这些内容，只保留当前工作区真实可计算的账户、资格、审批、回复、会议和来源数据。

一个信息更少但可信的页面，比一个看起来完整却无法解释的数据面板更有价值。

## 一次真实测试带来的修正

真实模型 smoke test 曾暴露实体漂移：正确的账户 ID 与不相关的公司名称同时出现在结果中。

我没有通过修改提示词掩盖问题，而是调整了系统边界：

- fixture 根据当前账户身份生成；
- 持久化 ID、名称和证据优先于模型叙述；
- 保存结果前执行字段归一化和后置校验；
- 增加故意注入错误公司名称的回归测试。

这个案例体现了项目最重要的设计原则：模型可以提出内容，但不能改写系统已经确认的事实。

## 如何查看

推荐按下面顺序演示：

1. Account Detail：证据、资格判断、联系人和下一步；
2. Mission Detail：目标如何变成可回放的执行计划；
3. Approval Review：消息如何结合证据进入人工决定；
4. Reply Inbox：回复如何形成下一步行动和负责人；
5. Analytics：当前闭环结果如何被真实记录。

完整讲解见 [3–5 分钟演示脚本](DEMO_SCRIPT.md)，测试与评测记录见
[作品评测报告](PORTFOLIO_EVALUATION.md)。

## 这个作品证明什么

这个项目想证明的不是“我会调用一个模型接口”，而是我能够：

- 从模糊业务目标中抽出稳定的操作链；
- 在产品、工作流、数据和模型之间划分责任；
- 把不确定输出转化为可观察、可限制、可测试的系统行为；
- 用真实界面和自动化证据验证规划，而不是停留在方案文档。
